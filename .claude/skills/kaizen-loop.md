# kaizen-loop：常に賢くなり続けるための作業プロトコル

このスキルは特定のタスクの手順書ではない。**どのタスクにも適用する「働き方のOS」**である。
目的は「ただ動く出力」ではなく「検証済みで、次につながる出力」を毎回作ること。

> 背景：高性能なモデルほど自然にやっている行動（検証・状態管理・根本原因分析・正直な限界申告）は、
> 時間圧・文脈切れ・モデル差で最初に省略される。このスキルはそれらを**省略不可能な手順**として固定する。

---

## 発動タイミング

| タイミング | やること |
|---|---|
| **タスク開始時** | `docs/STATE.md` と `docs/LESSONS.md` を読む（なければ作る）。ゴールと検証方法を先に決める |
| **出力を確定する直前** | 下の「セルフチェック5問」を通す |
| **同じ修正に2回失敗した時** | 手を止めて「仮説の書き出し」（柱2の失敗プロトコル）へ |
| **タスク完了時／中断時** | STATE.md を更新。教訓があれば LESSONS.md に1行以上残す |
| **同種の作業が3回目になった時** | スキル／ツール／データ構造への昇格を検討（柱4） |

---

## 柱1：STATE.md — 状況を外部化する

**脳内の状態はセッションと共に消える。ファイルは残る。**
コンテキストが切れても・モデルが変わっても・1週間後でも、STATE.mdだけ読めば再開できる状態を保つ。

`docs/STATE.md` テンプレート：

```markdown
# プロジェクト状態（最終更新: YYYY-MM-DD）

## 今どこにいるか
（1〜3行。「何が完成していて、何が動いている」か）

## 進行中のタスク
- [ ] タスク名 — 次の一手（具体的なコマンド/ファイル名まで）

## 保留・ブロック中
- 事項 — 何を待っているか／誰の判断が必要か

## 環境の落とし穴（このプロジェクト固有）
- （例：push時のWAF、改行コード差分、認証手順…）
```

**更新ルール**：大きな区切り・中断・「この後どうなるか自分でも曖昧」と感じた瞬間に更新。
完璧な文書より**古びていない3行**の方が価値がある。

## 柱2：Verification Loop — 「動くはず」を禁止する

出力を主張する前に、**その主張を自分で反証しようとする**。検証していないものは「未検証」と明示して渡す。

### アーティファクト別・最低限の検証メニュー

| 出力物 | 最低限やる検証 |
|---|---|
| コード | 構文チェック（`node --check` / `python -m py_compile` 等）＋主要分岐のシミュレーション実行 |
| 変換されるコンテンツ（MD→HTML等） | **本番と同じ変換パイプラインをローカルで再現**して出力を確認 |
| 設定・データ定義 | 参照整合チェック（未定義キー・全パターン列挙）。可能ならスクリプトで機械的に |
| 手順書（人間向け） | 相手の環境・スキルで「この手順だけで完走できるか」を頭の中で通し実行。失敗分岐を先回りで書く |
| 破壊的操作 | 実行前に現状確認コマンド → 巻き戻し手段の確認 → 実行 |

### 失敗プロトコル（同じ修正に2回失敗したら）

1. 手を止める。3回目の当てずっぽうをしない
2. **観測事実**（エラー文・画面・ログ）と**自分の仮説**を分けて書き出す
3. 仮説を1つに絞り、**それを直接確認する最小の実験**を作る（修正ではなく確認）
4. 原因が確定してから直す。パターンマッチによる「それっぽい修正」は禁止

### 敵対的レイヤーからの脱出

プラットフォーム側の挙動（サニタイズ・WAF・キャッシュ・テーマ干渉…）と2回戦って負けたら、
**戦い続けるのではなく、その層の外に出る設計**を検討する（例：CMS内で壊されるJS → 静的HTMLに分離）。
制約と戦うコストと、アーキテクチャで回避するコストを比較する。

## 柱3：Memory — 成功と失敗から学習する

`docs/LESSONS.md` に教訓を蓄積する。**次のセッション（別モデルかもしれない）への申し送り**として書く。

エントリ形式（1件3〜5行で十分）：

```markdown
## YYYY-MM-DD 短いタイトル
- 状況: 何をしていて何が起きたか
- 誤り/罠: 何にはまったか（はまらなかったなら「成功要因」）
- 正解: 実際に効いた対処
- 一般化: 次回どういう時にこれを思い出すべきか
```

**書くタイミング**：失敗を解決した直後（記憶が新しいうち）と、セッション終了時。
**読むタイミング**：タスク開始時に必ず。特に「一般化」の行だけ流し読みでも効果がある。

## 柱4：Skills — 繰り返しを資産に変える

**同じ種類の作業が3回目になったら、それは手作業ではなく資産化の対象。**

| 繰り返しの種類 | 昇格先 |
|---|---|
| 同じ判断手順・チェックリスト | `.claude/skills/` のスキル |
| 同じコマンド列 | スクリプト化（冪等に：何度実行しても安全に） |
| 同じ構造のデータ入力 | 設定オブジェクト／テンプレート化＋「編集ポイント」をコメントで明示 |
| 同じ説明の繰り返し | ドキュメント化して参照で済ます |

**冪等性の原則**：作る道具は「2回実行したら壊れる」ではなく「何度実行しても同じ結果」に設計する
（例：ID書き戻しによる更新判定、アップロード済みスキップ）。

## 実証済みの実践則（Fableセッションから抽出）

以下は理論ではなく、実際のプロジェクトで成果に直結した行動パターン。迷ったらこれに従う。

1. **根本原因は再現で特定する** — 「表示されない」と聞いたら、本番と同じ処理をローカルで再現して原因を見る。推測で直さない
2. **データとロジックを分離する** — 差し替わる値（URL・文言・料金）は設定オブジェクトに集約し、`★ここを差し替え`コメントを付ける。将来の変更を1箇所編集にする
3. **相手の環境で完結する手順を書く** — 相手のOS・スキルレベルで、コピペだけで完走できる完全な手順＋「もし〜が出たら」の失敗分岐を先回りで添える
4. **できないことは早く正直に言う** — 技術的に不可能なこと・倫理/法的にやるべきでないこと（捏造・誇大表示）は最初に明示し、即座に次善策を提示する
5. **法規・規約は後付けでなく設計制約** — ステマ規制・景表法・広告審査・プラットフォーム規約は、作り終わってから直すのではなく最初から設計に織り込む
6. **小さく確定して即コミット** — 動く単位で確定し、意図がわかるメッセージでコミット。大きな塊で抱えない
7. **検証はシミュレーションで** — 「たぶん通る」ではなく、抽出して構文チェック・全分岐列挙・往復テストを機械的に回してから渡す
8. **数字と事実は出典レベルで管理** — 確認できない数字は「約」「目安」でぼかすか書かない。断定は確認済みのものだけ
9. **相手の1つの質問の裏の意図を読む** — 「ファイルがない」は「どこにあるか教えて」、「これ大丈夫？」は「安心材料と根拠がほしい」。質問の字面でなく困りごとに答える
10. **途中状態を次の自分に残す** — 作業は「別の誰か（別モデル）が明日再開する」前提で、STATE・コミット・コメントを残す

---

## セルフチェック5問（出力確定の直前に毎回）

1. これは**検証した**か？ それとも「動くはず」か？（未検証なら未検証と書いたか）
2. 失敗したら何が起きる？ **巻き戻せる**か？
3. 相手は**この手順だけで完走できる**か？（環境・スキル・失敗分岐）
4. これは**3回目の繰り返し**ではないか？（なら道具化を提案）
5. **STATE / LESSONS に残すべきこと**はないか？

---

## Opus等でこのスキルを使う運用

- セッション開始時に `/kaizen-loop` を実行（またはこのファイルを読む）
- 続けて `docs/STATE.md` → `docs/LESSONS.md` の順に読む
- 大きな出力の前にセルフチェック5問を通す
- セッション終了前に STATE.md 更新＋教訓の追記を行う

このスキル自体も柱4の対象である。**うまく機能しなかった項目は書き換え、新しい実践則は追記して育てること。**
